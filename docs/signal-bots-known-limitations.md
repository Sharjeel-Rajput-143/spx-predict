# Signal bots - known limitations

Things that look like bugs but are deliberate for now. Each says why, and what would change it.

## The automation builder is a design tool, not a runtime

- **Saved flows don't run.** Flows, attached automations and symbol-scan settings are stored in the browser (`localStorage`, see `src/components/automation/builder/store.ts`). They are not sent to the server, are not read by the signal engine, and can't place an order or call a webhook. The UI marks them **Preview**. Clearing site data deletes them; they don't follow you to another browser.
- **Run test is a read-through.** It lists the steps in order (both paths of every decision) and evaluates nothing. The "Prevent automation from modifying bot" box is real UI but changes nothing, because there is nothing connected to modify.
- **Entry / Position criteria are saved, not enforced.** The 7 + 16 checklists are part of a design. The engine applies its own fixed guards (position, daily and allocation limits, leg overlap, strike validation) and does not read them.
- **Open Position settings don't drive strikes.** The engine builds strikes from the bot's offsets, width and quantity (Settings > Bot inputs). The built-in Bullish/Bearish flows are *drawn from* those inputs for reference; editing them is disabled.
- **To make a flow real** it would need a server-side store, a validator, and an executor that runs steps through the same guards, lock and decision log as a webhook signal. That replaces the spec'd fixed decision logic with user-defined logic and is a design decision, not a bolt-on.

## Builder details

- **Conditions are a fixed catalog, not a live search.** The condition picker offers a hand-written set of sentences (Stocks / Positions / Bot; an Indicators category is kept in the code but hidden, because this platform does no price analysis) and filters them as you type. It does not query market data or an indicator registry. Adding a condition means adding an entry to `CONDITION_CATALOG` in `builder/model.ts`.
- **The node menu has no "Move".** It offers Settings, Precede with..., Copy Action, Edit Caption, Edit Notes and Delete. Steps are placed with the + buttons and *Precede with...*; there's no drag-and-drop or "move to another branch".
- **Steps can only be appended** at the end of a branch, or inserted before an existing step. There is no insert-after or reorder.
- **Conditions are ANDed.** A Decision can stack several conditions; there is no OR / grouping.

## Position details

- **Shown as "-" on purpose:** market value, mid price, bid/ask, delta/theta/gamma/vega, alpha, EV and the probabilities. They need an option chain or a pricing model; nothing is estimated. Everything that follows from the trade itself is real: credit, capital at risk, max profit/loss, breakeven, reward/risk, OTM %, days in trade, and the expiry payoff diagram.
- **The payoff diagram is the expiry payoff**, not today's mark-to-market curve (that would need option prices). The blue pill is the live SPX quote when there is one, else SPX at open.
- **Exit Options are shown but disabled** (Edit / Reset stats, the "off" warning, five rows of "None"): profit targets and stop losses need live option prices, and there are no high/low watermarks to show.
- **Override is disabled.** There is no way to override a position's status in Phase 1.
- **Move** reassigns an *open* position to another bot on the *same account* that is set up, not archived, and has room under its limits. It moves the position's counts too (the target's "opened today" goes up). Both bots get a "Position moved" decision.

## Automation log (the run replay)

- **Only runs from now on have a trace.** The engine now records, for every signal and manual action, the checks it walked through (each with its Yes/No and the real value it compared) and the orders it placed (with the exact legs and a frozen copy of their settings). Entries from before that was added only have their outcome, and the log says so.
- **The checks are the engine's own, not Option Alpha's.** A flip reads: bot on, (trigger on), market hours, not a duplicate, opposite side held?, no close in flight, **Close card**, room for the wanted side, position / daily / allocation limits, strikes valid, no leg overlap, **Open card**. A run that stops early shows only the checks it reached.
- **The "as sent" tooltip lists what the engine actually sends** - for a close that's the quantity and confirm timeout (a close order carries no limit price); for an open it's the limit credit, quantity, expiry, how each strike was derived, and the fill timeout. There is no Memo or Tags field because the engine's orders don't have them.
- **View position** opens the position's details if it still exists; it's disabled once a bot's history has been deleted.
- **A crash mid-run is logged too.** An unexpected error leaves an "Unexpected error" decision row and a trace of the steps reached, then still surfaces to the caller.
- **Clear Log hides, it doesn't delete** - traces stay in the export store and in the engine's duplicate protection.

## Not built (Phase 1 has nothing behind them)

- **Exit Options** (profit target / stop loss on a position) - needs live option prices.
- **P/L, Change, Return, win rate and the rest** show "-" until the executor reports fill prices. `AUTOMATION_MOCK_PRICING=simulated` invents close prices for demos; the bot page then says every figure is fictional.
- **Scan Speeds and watchlist scanning** - these bots are driven by webhook signals, not polling. The Bot symbols panel saves its settings as a preview only; the engine trades SPX.
- **Transfer History**, **Backtester**, and the rest of the Option Alpha sidebar (Home, Trade Ideas, Screener, Community, More Tools).
- **"Show tags" on positions** - positions aren't tagged; bots are.
- **Live accounts.** Every bot is paper (mock executor). The Live filter exists but matches nothing until a real broker (Phase 2) is connected. Brokerage account numbers, when they exist, are masked in the UI.

## Behaviour worth knowing

- **An empty bot can't trade until its inputs are set.** Name, account and allocation are all it needs to exist, but the strike offsets and expected credit have no defaults, so it shows *Setup needed* and refuses to switch on until they're entered.
- **Day trading "Not allowed"** holds a same-day position to expiry instead of flipping it; manual closes still work.
- **Sign-in** is skipped in development when `AUTOMATION_STATUS_PASSWORD` is unset, and a production build refuses all access without one.

## NDX bot (ndx_ema_bias)

- It is the same engine and webhook as SPX, configured by `BOT_NDX_EMA_BIAS_*` env values. It works with no settings: strike spacing 5, option root NDXP, a fallback credit of 3.5 (used only when there is no live quote and for the risk check), and the end-of-day sweep at 16:05 ET (ten minutes before NDX options stop trading at 4:15pm). The signal-price sanity range is optional. All can be overridden; the sandbox probe prints the real spacing and root. A wrong value (not a number, a width that isn't a multiple of the spacing) is still refused, naming it.
- Still to verify before live use (marked TODO in `.env.example`): the NDXP root and a 0DTE series every weekday, the real strike increment, the series' final trading time, and the broker. Mock executor only.
- `symbol_mismatch` is checked only when the alert sends a `symbol`. A body with no symbol is protected by the price range alone, so keep the alert body from the addendum.
- Bots are only ever created in the UI as SPX; NDX is the env-configured built-in. Extra NDX bots from the New Bot form are accepted by validation but the form has no NDX option yet.
- The allocation check keeps its existing outcome name, `allocation_limit_reached` (the addendum calls it `allocation_exceeded`).
- Broker research (Tradier) and the disabled executor are in `docs/tradier-executor-research.md`.

## Testing mode and the Tradier executor

- The admin page (Automation > Testing, `/automation/status`) is the demo surface: positions with legs and credit, orders and their states, the decisions under each alert, bot on/off, **Send test alert**, **Reset test data**. Every trade on the mock executor is labelled TEST.
- Send test alert is mock-only. It builds the TradingView body on the server (the secret never reaches the browser) and calls the same ingest function as the webhook. It only differs by an internal `test` flag, which a webhook body cannot set.
- A test alert runs outside trading hours only with `AUTOMATION_TEST_MODE=true`; the trace then says "Testing mode: clock check skipped". Real alerts always obey the clock.
- The mock fills at the configured expected credit and reports no close price, so credit shows the configured number and P/L stays blank. Nothing here says anything about real fills.
- Reset test data wipes every recorded alert, position, order, decision and run (bots and settings stay) and is refused unless the mock executor is selected.
- `EXECUTOR=tradier` is implemented but disabled and unverified against any real account - see the TODO list in `docs/tradier-executor-research.md`. `symbol_mismatch` and `price_out_of_range` leave the signal row as "accepted" (the route answers 200); the decision log carries the outcome.

## Settings taken from the live Option Alpha SPX bot

- **Offsets are decimals now.** The live bot puts the short strike 0.01 beyond the price. Both built-in bots default to put -0.01 / call +0.01. For SPX that is the owner's real value; for NDX it is the SPX bot's value copied over - **owner to confirm for NDX**. The NDX strike increment is still required, with no default.
- **Rounding mode (`*_STRIKE_ROUNDING`, default `outward`).** The short put rounds down and the short call rounds up (the out-of-the-money side); `nearest` is the alternative. **TODO: verify "outward" against Option Alpha's real behavior.** This is the default for every bot, so an SPX signal at a price like 7720.5 now gives a call spread at 7745/7750 where it used to give 7740/7745. Set `BOT_SPX_EMA_BIAS_STRIKE_ROUNDING=nearest` to get the old result.
- **Every decision records how its strikes were chosen**: price, signed offset, target (price + offset), rounding mode, increment and the chosen short/long strikes - in the decision's detail, on the status page under each alert, and in the run trace.
- **Order price is a percent of bid/ask** (`*_OPEN_PRICE_PERCENT`, `*_CLOSE_PRICE_PERCENT`, default 100, shown on the bot's Settings and on the order). **TODO: the exact meaning of "100% of bid/ask" is unconfirmed**, and the mock has no bid/ask, so nothing is computed from it yet - it travels with the order for a real executor. The credit-below-width check is unchanged.
- **Position limits per bot.** SPX holds up to 3 positions by default (`BOT_SPX_EMA_BIAS_TOTAL_POSITION_LIMIT`), NDX stays at 1; a limit set under Settings > Safeguards still wins. One position per side stays the default, so the live bot's flows (close the opposite side, then open if none is open) are unchanged.
- **Activity alerts** (opened, closed, warning, error) are recorded for each bot (per-bot switches under Settings > Alerts, all on) and listed on the status page. Warnings are safeguard blocks (limits, symbol mismatch, price out of range, overlap); errors are failures (executor error, rejected or timed-out orders, bad config). Routine skips (bot off, outside hours, same side already held, duplicates, dry run) raise none. **Email is optional and off by default, and no mail sender is wired**: with `ALERT_EMAIL_ENABLED=true` and `ALERT_EMAIL_TO` set, each alert is only marked "queued". Choosing a provider is the owner's call.
- **The two-stage flip stays**: close, wait for the confirmation, then open - safer than Option Alpha's single path.
- **Option Alpha's "Close Monitor" automations were first left out on purpose** (see "Close Monitors" at the end: the Bullish one is now built, off by default, with a guard). It uses them to sweep wrong-side positions. If a similar check is wanted later it must compare against the **latest confirmed signal**, so it can never close the correct side.

## Order pricing and the other Option Alpha options (decided)

- **The mechanism is understood.** "100% of bid/ask" on the live bot is the **Final Price** setting inside a **SmartPricing** ladder running in **Normal** mode: up to four timed limit orders, ten seconds apart, the last one reaching the full bid/ask spread. Close Position uses the same preset, with quantity 100% of the position.
- **SmartPricing is now built** (`smartPricing.ts`, `placeAndWatch.ts`), because the broker decision moved toward real trading. When the executor can quote the spread (Tradier can; the mock can't unless a test gives it a market) an order walks the ladder: Normal = up to 4 prices, 10 seconds each, from the mid toward the final price (`*_OPEN_PRICE_PERCENT` / `*_CLOSE_PRICE_PERCENT` of the way across bid/ask); Fast = 3 x 5s; Patient = 5 x 20s; Off = one limit order at the final price. A rung that doesn't fill is canceled and the next price sent; the last price waits the full timeout (120s), then cancels. A partial fill stops the walk and waits for the rest, restarting the full timeout on each further partial fill; the position keeps what filled. Every rung is its own order row; the decision log carries the ladder.
- **Without live quotes nothing changes:** one price and the 120 second timeout, as before. A quote that fails, or isn't there, falls back to that one price and says so in the log. An unusable market (no bid, crossed, a mid of zero or less) refuses to open rather than guess.
- **Not verified against any real account.** The tick size (0.05 is assumed, TODO), the `/markets/quotes` response for index options, whether the sandbox serves them, and how Tradier reports fill prices all need a real sandbox run - see `docs/going-live-checklist.md`. **Final check with Blue:** only whether the live bot was ever switched off Normal.
- **Intentionally out of scope (unchanged):** the other strike modes (delta, percent, expected move, GEX...), the other position-sizing modes (risk caps, percent of allocation, martingale), exit options (profit taking, stop loss, trailing stop...) and the entry and position filters. The live bot uses none of them, so there is nothing in its behavior to match. The engine stays as is: flat offsets for strikes, fixed contract sizing, no exit logic, hold to expiry with the end-of-day sweep. Any of these gets built only when specifically asked for.
- **Other points from the same review:** OA's start/end times are choices on a 5-minute grid (ours take any HH:MM); OA has no weekday condition (our guard adds weekdays and the NYSE calendar); its position-count check ("exactly or more than 1 ... any status") matches ours, which counts opening, open and closing positions; its expiration is exactly 0 days, any series (not monthlys only), calendar days; NDX is not a searchable symbol there.

## The built-in canvas is live; the flows you design are still previews

- **Bullish and Bearish signal (Settings > Automations):** the canvas now opens as "Built-in · live". Click a node to edit its real values: the market time window (start and end on the 5-minute marks, or back to the default window), the open step (short strike offset with decimals, rounding, width, contracts, expected credit, price % of bid/ask) and the close step (price % of bid/ask). Save writes them to the bot's settings - the same ones as Settings > Bot inputs - and they apply to the next signal; an open position keeps the values it was opened with. The canvas redraws from the saved values.
- **The shape of the flow is fixed.** It is the engine's logic, so steps can't be added, removed or reordered there, and the position-check nodes are explanations, not editable. Duplicate protection, the limits (Settings > Safeguards), the strike checks and the failsafe aren't drawn.
- **Shared values.** Window, rounding, width, contracts, credit and price % belong to the bot, so editing them on the Bullish canvas also changes the Bearish one. Only the short offset is per side.
- **Saving stores the bot's inputs with the bot**, which overrides its environment settings from then on (as Bot inputs already did for a built-in bot). The values it didn't show - option root, price range, sweep time, position limit - are carried over unchanged.
- **Designs you build with the + button are unchanged:** they save to this browser only and don't reach the engine.


## Settings page (modelled on Option Alpha's)

- **Sections:** General, Trading Accounts, Bot Archive, Webhooks - in this app's own styling. Option Alpha's Subscription Plan, Community Profile and Referral Program are about their business, not this engine, and are not built. Personal information and Change Password are omitted too: sign-in is one shared password (`AUTOMATION_STATUS_PASSWORD`).
- **Real, saved settings:** the default trading window (Bot schedule; a bot's own window on its canvas still wins), email preferences, session timeout, and text size (this browser only). Bot Archive restores and deletes for real.
- **Email is preferences only.** No mail sender is connected, so enabling it queues each alert and sends nothing. Which provider to use is the owner's call.
- **Session timeout** only matters when sign-in is required (a password is set). Two-step authentication is shown as not available.
- **Trading Accounts** is read-only: the executor in use and the accounts the bots name. Add account is disabled until the broker decision.
- **Webhooks** now leads with the alerts this app *receives*: the URL, whether `WEBHOOK_SECRET` is set (never its value), and a ready TradingView message for each bot and direction with a `<SECRET>` placeholder. The old outbound Option Alpha connections sit behind a "Show connections" button, so opening Settings no longer loads them.
- **Exit options and in-the-money positions:** unlike Option Alpha there are no exit options and no auto-close, so these show as explanations, not controls.

## Named webhooks (like Option Alpha's)

- **Settings > Webhooks > Your webhooks:** create a webhook with a name (see "Webhook attachment" below: it is attached to a trigger afterwards). It gets a unique secret URL (`/api/webhook/hook/<token>`). A call to it means that signal for that bot - paste it into a TradingView alert. The alert message needs only the price: `{"price":{{close}},"bar_time":"{{timenow}}","interval":"{{interval}}"}` (a plain number works too). With no price, the bot's underlying's live quote is used if it is under 5 minutes old; otherwise the call is refused.
- **One trigger per webhook (the bot and direction come from the trigger it is attached to).** Option Alpha lets one webhook trigger several bots; here each bot's price differs (SPX vs NDX), so each bot gets its own. Make a Bullish and a Bearish webhook per bot.
- **The URL is the credential.** Whoever has it can trigger that bot's signal, so treat it like a password. Switching a webhook off or deleting it makes the URL answer 404, the same as a URL that never existed. A body can't change the bot, the signal or turn on test mode.
- **Once a minute.** A webhook called again within a minute is ignored, as in Option Alpha; the signal log shows it as rejected (`webhook_rate_limited`). The engine's own duplicate protection (an identical signal within 2 minutes) still applies on top.
- The older single URL (`/api/webhook/tradingview`, with the secret and the bot in the message body) still works, but it is no longer shown on the Webhooks page: the page lists only the named webhooks. Its `WEBHOOK_SECRET` is still needed for it.
- TradingView only allows webhook alerts on accounts with two-factor authentication on.
- See `docs/deploying.md`: webhooks only work on a host that stays running and can write its records - not on Vercel as it stands.

## The SPX bot is hidden for now

The built-in SPX bot starts archived and switched off, so it is out of the Automation list, the Testing page and the webhook choices. It is under Settings > Bot Archive: Restore brings it back (and it stays back). Set `BOT_SPX_EMA_BIAS_HIDDEN=false` to show it from the start on a new deployment. A signal that reaches it while hidden is logged as "Bot is off" and does nothing. Its code, settings and history are untouched.

## NDX scope update: the eight Option Alpha changes (NDX bot only)

SPX stays in Option Alpha and is not part of this engine. Only `ndx_ema_bias` is configured and on; the per-bot structure stays so a second bot can be added later, but nothing is built for one.

- **10 errors in one trading day switch the bot off** (`error_failsafe`): an error alert is raised, the reason is written to the bot log and shown as "Needs attention" on the status page. The count is by New York trading date, so it starts again the next trading day - **the bot itself stays off until a person switches it back on** (assumption: Option Alpha's wording is "resets next trading day"; say if the bot should switch itself back on).
- **A safeguard limit switches the bot off.** The position limit, the daily limit and the allocation limit each switch the bot off, say why in the decision (bot log, run trace, alert) and set "Needs attention" with the reason. A person checks and switches it on. "Already in position" (a repeat signal on a side already held) is a plain skip, not a limit, so it does not switch the bot off. **While the bot is off, a webhook can still close the opposite position and can never open one** (see "Bot off, kill switch" below); the end-of-day sweep and **Close position** work either way.
- **The price ladder** (SmartPricing): Normal 4 prices x 10s, Fast 3 x 5s, Patient 5 x 20s, from the mid toward the bid when selling (the ask when buying back); the last price waits 2 minutes, then cancels. **Final price** is the setting (percent of the way from the mid to the bid/ask, default 100); it replaces the old "price aggression" TODO. **Every price tried is a line in the run trace** (price, how long it waited, what happened). It needs live quotes: the mock has none, so there it is one price.
- **Partial fills:** wait for the rest; each new partial fill restarts the 2 minute timer; on timeout the remainder is canceled and the position is **open at the partial quantity** (the log says "1 of 3 contracts"). A *close* that only partly fills is different: the position stays **closing**, keeps its slot in the limits, the bot is flagged, and a person clears it.
- **Closing counts as held, like Option Alpha's "any status".** In the "opposite position" and "already in position" checks, a position in `closing` counts. A closing position never gets a second close order. If an opposite signal arrives while that close is still working, the flip **waits for it to be confirmed** (the same wait and timeout as a close it sends itself) and only then runs the Open step; if it never confirms, the run stops, the bot is flagged, it counts as an error, and the other side is not opened. A closing position with **no order working** behind it (a stuck or failed close) is not retried either: the run stops with `close_in_flight` and it stays for a person to clear (**Close position** on the page is the manual retry). A closing position also keeps its slot in the position, daily and allocation limits and the overlap check, so nothing can open before the old position is gone. The flip is still close, confirm, then open.
- **Identical actions and overlapping strikes.** An identical signal is a duplicate; a side with an order in flight can't be opened again; opening is refused when the same underlying, strike and expiry (and option type) already exist in the bot. **A failed or stuck order keeps its slot**: an order whose outcome is unknown (the executor threw, or we lost track of it) leaves the position `opening` or `closing`, counts against the limits and the allocation, and stays until a person clears it. An order that was cleanly canceled with nothing filled leaves nothing behind, so it frees its slot (it still counts toward the daily total).
- **Do not place manual orders on positions the bot manages** - a note on the status page and in the testing walkthrough.
- **End-of-day sweep, three modes** (Settings > Bot inputs > End-of-day sweep, or `BOT_NDX_EMA_BIAS_EOD_SWEEP_MODE`): *estimate* (default) expires each held position and works its P/L out from the underlying's price (the spread's value at that price from its strikes and credit), labelled **estimated** everywhere; *market* sends a market close order (no limit price) and the position closes on its fill - a close that fails flags the bot and leaves the position for a person; *manual* expires it and lists it under **Waiting for your P/L** on the status page, where a person types the result in (it must be possible for the trade: no more than the credit, no worse than the max loss). It runs at the bot's own sweep time, **16:05 ET by default - ten minutes before the NDX series' 4:15pm close** - inside the bot's lock, even when the bot is switched off.
  - *Estimate needs a fresh underlying price* (the live quote, up to 30 minutes old). With none, nothing is guessed: the position waits for a manual entry. The estimate is exact only if the underlying's settlement value matches the price used; it is a stand-in for the broker's statement, which stays the truth.
  - Positions left over from an earlier day (the safety net that expires them when the next signal arrives) have no result either and appear under **Waiting for your P/L**.

## The signal, and the decision flow (NDX)

- **The only input is the TradingView webhook call**, bullish or bearish, for `ndx_ema_bias`. The EMA 9/20 setup lives only in TradingView: this platform has no EMA or indicator settings and does no price analysis, and does not decide direction. (The id `ndx_ema_bias` and the `BOT_NDX_EMA_BIAS_*` prefix are a legacy name; the bot is shown as **NDX Bias Bot**.) Only the confirmed bullish and bearish alerts should call the webhook; any other alert causes duplicate entries.
- **Two automations, as in Option Alpha's BullishSpx / BearishSpx:** Bullish (short put spread) and Bearish (short call spread). The order of checks: bot on, trigger on -> market window (weekdays and holidays too) -> price sanity -> duplicate -> **close the opposite side** (confirmed before going on) -> **Open step**: already holding the wanted side? -> position limit -> daily limit -> strikes -> allocation -> overlap -> price -> order. Limits are checked at the Open step, after the close is confirmed. No Close Monitor exists; the only things that close or settle a position are the opposite signal, the Close position button, and the end-of-day sweep.
- **Strike price source** (`BOT_NDX_EMA_BIAS_STRIKE_PRICE_SOURCE`, or Settings > Bot inputs): `alert` (default) builds the strikes from the price recorded when the call arrived (for a webhook that is the bot's own live quote at that moment, never a price sent by TradingView: a webhook is only a trigger, as in Option Alpha); `live` takes a quote when the Open step runs (after a flip's close, that can be minutes after the alert). Every opening decision logs which was used, the price and its age (seconds); the price-range check runs on whichever price is used. A live quote older than `STRIKE_QUOTE_MAX_AGE_SECONDS` (default 60), or none, means the bot refuses to open (`no_live_price`) - it never falls back to the price recorded at the call quietly. Default `alert` on the mock and the Tradier sandbox (Tradier's FAQ: all sandbox market data is delayed 15 minutes). **The only live quote source today is the app's own price feed (Google / Yahoo); its "age" is when it last received a price, not an exchange timestamp, so a feed that is itself delayed can't be detected by age. Use `live` only once a real-time source is connected.**
- **Dry run runs the whole flow and withholds every order**, the flip's close included: it logs "would close" and "would open", judges the Open step as if the close had happened (so a limit of one does not trip on the position it would close), and changes nothing.
- **A failed close** stops the run, flags the bot, never opens the other side, and counts as an error toward the 10-error failsafe.
- **No global switch.** There is no switch across all bots. Per bot there are three: the bot's On/Off, the per-direction triggers, and the kill switch (next section).
- **Hidden from the NDX pages:** the older indicator-rule feature (`/automations/rules`) is no longer linked from the Automation page. It is still in the code and still opens at its URL. Settings > Webhooks no longer has its "Option Alpha connections (outbound)" section (removed later).

## Bot off, kill switch, and "Always On"

- **"Always On" in Option Alpha is copied only for closes.** In Option Alpha the BullishSpx trigger is "Always On": it runs even when the bot's automations are off. Here, with the bot's **On/Off switch off** - whether a person switched it off, or a safeguard limit or the 10-error failsafe tripped it - a webhook may still run the **close** part of the flow (the flip's close of the opposite position) and may **never open** a position. The log says "Bot off, close only" when it closes, and the Open step is then blocked with the reason "Bot off": the run ends with no new position. With nothing to close (a same-side signal, or nothing held) the run does nothing and logs "Bot off". The Bearish direction is the mirror. **Opens always respect the bot switch**, including a position placed by hand from the UI.
- **Rules for that close are the usual ones:** the hours guard still applies; one close per position, never a second; a failed close counts as an error toward the 10-error failsafe, stops the run and flags the bot; it is never retried automatically (a closing position with no order working stays for a person to clear). In dry run the close is shown as "would close" and nothing is sent.
- **The kill switch is separate** from the bot's On/Off and stops **every webhook run completely, closes included**. It is a per-bot switch on the Testing page and in the bot's header, turned on and off only by a person (it does not trip by itself). It wins over the bot switch. Until now the engine had no separate kill switch: the bot's On/Off was called that.
- **Never blocked by either switch:** the end-of-day sweep (all three modes) and the **Close position** button.

## Webhook attachment (NDX Bias Bot)

- **Attached from the trigger.** A webhook is created in Settings > Webhooks with just a name (or with the **+** in the panel). In the NDX Bias Bot's Settings > Automations, the **gear** on the Bullish trigger and on the Bearish trigger opens **Edit Settings**, laid out like Option Alpha's: **Automation** (the trigger's own flow, fixed; New is disabled), **Schedule** (Webhook; the other schedule types are listed but disabled), **Webhook** (a dropdown of every webhook with its on/off status and a copy icon on each row, and **+** to create one), **Always On**, **Save**; below it **Detach**, the URL (masked, Reveal and Copy) and **Test hook**.
- **Always On is a real, per-trigger setting** (default on, as in Option Alpha): with the bot off, an Always On trigger may still run its close part and never opens. With Always On off, a trigger does nothing while the bot is off. The kill switch beats both. What is attached stays until a person changes or detaches it, and survives a restart.
- **One webhook, one trigger.** A webhook attached to the other trigger is in the dropdown but unavailable, with the reason ("Already attached to the Bullish trigger of NDX Bias Bot (one webhook, one trigger)"); the server refuses it too. A trigger holds one webhook: choosing another **changes** it (the first becomes unattached). Detach it first to move a webhook to the other trigger.
- **A call to an unattached webhook is refused** (409, "isn't attached to a trigger"); a switched-off one or an unknown URL answers 404, as before. Webhooks created before this (with a bot and a direction) are simply already attached.
- **Attach, change, detach (and deleting an attached webhook) are logged** in the bot's log as `webhook_attached`, `webhook_changed` and `webhook_detached`, with names only - never the URL.
- **Secrets are never shown in full.** Lists and the trigger panel carry only the URL with the token masked (last four characters). The full URL comes from `GET /api/automation/webhooks/[id]/url` on **Reveal** or **Copy** (signed-in only, never cached) and is never logged. The secret is stored in `webhooks.json` in the data folder, which is in `.gitignore` (`data/`) and has never been committed. **Back-ups of the data folder contain the secrets: treat them like passwords.**

## Storage layer (JSON files today, a database later)

- **One interface.** The engine, the routes and the pages only call a `Repository` (`src/lib/automation/storage/repository.ts`): all, get, query, insert, update, remove. Only `storage/jsonFileBackend.ts` opens a file. A database implementation of the same interface can replace it with no engine change.
- **Folder:** `AUTOMATION_DATA_DIR` (default `data/automation`, git-ignored). One file per collection (`bots.json`, `signals.json`, `positions.json`, `orders.json`, `decisions.json`, `errors.json`, `runs.json`, `alerts.json`, `webhooks.json`, `settings.json`, `templates.json`) plus `meta.json`. There is no separate `counters.json`: the error and daily counters are worked out from the records by New York date, so they can't drift from them.
- **Every file is `{ "schemaVersion": 1, "collection": "...", "items": [...] }`.** A folder from before this (bare arrays) is upgraded in place on first start. A folder written by a newer version is refused.
- **Atomic writes:** the new content goes to a temp file, is flushed to disk (`fsync`), then renamed over the real file. A failed write leaves the old file and the in-memory copy untouched. `AUTOMATION_STORAGE_FSYNC=false` skips the flush (the test suite does; never on a real host).
- **A damaged or missing file is an error, never an empty start.** Invalid JSON, the wrong shape, no schema version, an item without an id, the wrong collection, or a file missing from a folder that was set up: the engine stops with a message naming the file (webhooks answer 503 and the status page shows it), and the file is not touched. Restore it from a backup, or move it aside to start that collection fresh on purpose. (Before this, an unreadable file was silently read as empty.)
- **One writer.** The per-bot lock orders the engine's writes within the one process; run a single instance (see `docs/deploying.md`).

## Close Monitors (Bullish and Bearish, both off for now)

- **What it is.** Option Alpha's "BullishSpx Close Monitor" is a sweep: "Bot has exactly or more than 1 position with Short call spread type and any status" -> Close Position (100% of the position, 100% of bid/ask). In Option Alpha it runs every scan inside 9:35am-3:55pm and is **switched off** on the live bot. Here it is a row under Settings > Automations > Monitors ("Bullish Close Monitor", window, toggle, gear, canvas), **off by default**.
- **Why it isn't a literal copy.** Option Alpha's version closes *any* short call spread whenever it runs. In a bot that also holds the Bearish side, that closes the position a bearish signal has just opened - it fights the flip, which is why it is off there. This one adds a second check, "the latest confirmed signal is bullish", so it **only closes a position that is against the latest confirmed signal and never the side that signal wants**. The canvas shows both checks.
- **"Confirmed" means the engine acted on it.** A signal that was a duplicate, outside the window, the wrong symbol, out of the price range, for a switched-off trigger, or received with the bot off or the kill switch on is ignored when looking for the latest one. A signal still being processed is unknown. With no confirmed signal, it does nothing.
- **Only the bot's own, only `open`.** It skips a position that is already closing or has a close order working (one close per position, never a second, never retried), one that is still opening, and one a person placed by hand.
- **It needs** the bot on, the kill switch off, the bot's trading window (weekdays, holidays), and runs inside the bot's lock so it never overlaps a signal. A failed close is an error (it counts toward the 10-error failsafe), flags the bot and stops there. Dry run logs "would close" and sends nothing. The close uses the bot's own close settings (Final price, SmartPricing, confirm timeout).
- **Memo and Tags** (the Close Position form) are real: written on the position it closes. Price and quantity are the bot's own settings and not edited there. "Discard expiring OTM long leg(s) with no bid price" is shown disabled (a spread closes as one multi-leg order; NDX options are cash settled).
- **Runs once a minute** in the server's scheduler (the "Every 1m" in Scan Speeds), so it needs the always-on host (see `docs/deploying.md`); it is quiet when there is nothing to do and only writes a log row and a run trace when it acts (`monitor_closed`).
- **Never needed by the end-of-day sweep or Close position**, which work with every monitor off.
- **Both monitors are off for now, and their switches are locked off in the UI.** The bot already closes the opposite side on every signal (the flip), so there is nothing for a monitor to add yet; they will be attached to the triggers later. The Bearish Close Monitor (a short put spread, when the latest confirmed signal is bearish) is the same code with the sides swapped, with its own row, gear and canvas. To switch one on later, un-lock the switch in `SettingsTab.tsx` (the engine, the API patch `monitors` and the tests already support it).

## Webhooks page and theme

- **Settings > Webhooks follows Option Alpha's layout:** an intro (what a webhook is), the once-a-minute rule in red, a "keep your webhooks secret and safe" box, a **New Webhook** button, then the list. **New Webhook** opens a slide-over with a Name (and "You'll use this name to reference it in your bots.") and **Create**. The webhook starts unattached; attach it from a bot's Bullish or Bearish trigger. Each row is laid out like Option Alpha's: the name, **Test Hook** (grey unless the webhook is on and attached, on the mock or Tradier sandbox), a **pencil** (rename, switch on or off), a **trash can** only while nothing uses it (an attached webhook is detached first), **Usages: N bots** (opens to show the trigger it is attached to), and **URL:** masked with a copy icon (Reveal is a small link next to it).
- **Light mode is the default.** Dark mode is still there behind the theme button, and a person's choice is remembered (under its own key). The theme the app used to save automatically is ignored, so everyone starts light once.
- **The Webhooks page lists only the webhooks.** The "Use it in a TradingView alert" steps, the shared-URL box and the per-bot alert messages were removed from the page (the alert message for a named webhook is `{"price":{{close}},"bar_time":"{{timenow}}","interval":"{{interval}}"}`, or just the price). One warning stays in the intro: only the confirmed bullish and bearish alerts should call the webhook, because extra alerts cause duplicate entries. The "Option Alpha connections (outbound)" section (Show connections) was removed from the page too. The old Rules module and its code are untouched and its URLs still open (`/automations/rules`), and the stored connections are untouched; they just aren't reachable from Settings any more.
